# Open Decisions and Known Port Gaps

Found while porting modules mechanically. Each needs an owner decision or a later spine change. Delete an entry once it is resolved.

## Decisions

1. **Where dock state lives. Settled 2026-11-27 (follow the C++):** in the dock module, reached through `DockFacet`. The `dock_closed` / `dock_crippled` stand-ins are gone.
2. **Default `XferSave` version.** The reference library is built with `RETAIL_COMPATIBLE_XFER_SAVE=1`, so `PoisonedBehavior` saves version 2. With `retail-xfer-save` off, the crate writes version 3. `golden_wp53_c1` strips the appended source id and compares it separately; `FlammableUpdate` (version 1 against 2) is handled the same way in `golden_pkt330_327_fire`. Should default features match 0 or 1?
3. **AI random-number draws.** `AIUpdateInterface` is unported. Its draws are imitated in `sim/mod.rs` (`ai_construct`, `ai_init_state_machine`, `ai_idle`). The real port must take them over.
4. **Shared and redirected passenger lists. Decided 2026-11-26 (owner: do what a faithful port does).** The contain getters now take `(sim, ctx)`, as the C++ virtuals reach the tunnel tracker and the rider's contain module. `PKT-300` and `PKT-264` are ported; `PKT-284` is unblocked.
5. **Containment override hooks. Decided 2026-11-26: yes, follow the C++ virtual calls.** `ContainBehavior` has hooks for `addToContainList`, `removeFromContain` and the list getters, but not yet for `addToContain`, `isEnclosingContainerFor` or `isSpecialOverlordStyleContainer`. Add those with the `OverlordContain` port. `HelixContain` (`PKT-275`) implements the facets itself.
6. **Settled 2026-11-27 (follow the C++):** `LandMineFacet::set_scoot_parms` takes the sim and context.
7. **Settled 2026-11-27 (follow the C++):** the overlap query, footprint operations and cliff cells that minefield placement needs are ported.
8. **Where a bridge's tower table lives.** `BridgeTowerBehavior` (`PKT-262`) asks the bridge module through `BridgeFacet::get_tower_id`, as C++ does. `link_bridge_tower` writes a second table, `SimWorld::bridge_links`, which nothing reads. The `BridgeBehavior` port should settle on one.
9. **Where barrel counts come from.** `Weapon::privateFireWeapon` reads `Drawable::getBarrelCount`, which comes from the model's bones, and the result is saved with the weapon. The port loads no models, so `ObjectRecord::weapon_barrel_count` stays 0 outside tests. Replay parity needs the counts from somewhere.
10. **How ported Rust reaches the playable game.** The playable game is the C++ engine; the last phase of `PLAN.md` yields only a headless simulator. Options: (a) keep porting and aim at a headless simulator that later needs its own client; (b) build the adapter and `SimApi` over C++ to move modules into the game one at a time; (c) swap only leaf code. Needs the owner. A trial of (b) with one module was done on 2026-11-27:
    - **It works.** The unmodified Rust `LifetimeUpdate` (`PKT-339`) runs in the engine and all 996 checkpoints match.
    - **One-off cost, now paid:** `scripts/gen_engine_sim.py` writes the `SimView`/`SimApi` impl (293 methods; unconnected ones abort with their name), plus about 100 hand-written lines in `engine_sim.rs`.
    - **Per-module cost:** about 60 lines of Rust entry points and 120 lines of C++ for 7 connected methods. The C++ module still owns the state, `crc` and `xfer`, so each further field has to be passed both ways.
    - **The limit:** 10 methods return references into Rust-owned data (`object`, `object_mut`, `rules`, `module_data`, `terrain` and others). 43 of the 64 source files that implement `BehaviorModule` call one directly. A callback cannot answer these; C++ state would have to be mirrored into Rust records, or the traits changed and those modules edited. Of the other 21, 13 make at most three direct `sim` calls and import no module helper. These counts miss calls made through shared helpers, so they flatter the adapter.
    - **Recommendation:** use the adapter for leaf modules where running in the real engine is worth it as a check on the port. Do not plan on it to move the simulation into the game: that needs the traits redesigned first. Playing the game does not depend on either, and a swap changes nothing the player sees.
11. **Whether to port the unit AI.** `AI_PORT_PLAN.md` splits it into slices of about 40 workers (12 to 20 million tokens before rework, an estimate); the first moving unit is about 15. It serves a headless simulator, not the playable game (item 10). Working assumptions until the owner says otherwise: reproduce the retail pathfinding and AI-group quirks the reference runs; leave computer opponents and real map loading for later; keep item 2 as it is. Only slice S0 is being started.

## Known gaps

- A module cannot be re-entered while it executes. `SupplyWarehouseCripplingBehavior` and `TechBuildingBehavior` apply their own self-callbacks inline instead.
- `BridgeScaffoldBehavior`: zero speed on a zero-length leg gives NaN positions. The reference then destroys the object from outside the module; Rust does not. `gen_wp53_c1.cpp` excludes those inputs, so no vector covers this.
- An unknown `PulseFX` name stays set in Rust but becomes null in C++.
- `capture_object` / `set_object_team` leave out the rest of `Object::onCapture`: `cancelAllTasks` on a dozer, clearing the `SCRIPT_UNSELLABLE` status and a skirmish AI selling a captured faction building.
- With `retail-crc`, `WeaponTemplate::get_delay_between_shots` returns the maximum when the minimum exceeds it; the retail PRNG helper draws a value there. The default build matches.
- `FloatUpdate` over dry ground: C++ writes an uninitialised `waterZ` to the object, so there is no value to match. The port writes 0.
- `ProneUpdate` skips the model condition for an object without a drawable, where C++ would crash.
- `PKT-307`, `PKT-343` and `PKT-364` are header-only manifest entries for modules ported under another packet (`PKT-308`, `PKT-281`, `PKT-233`). `PORT_MAP.md` still lists them as unported.
- `WeaponTemplate::fireWeaponTemplate` is unported. `fire_weapon_template` only records the shot, so range checks, projectiles, damage and the two logic PRNG draws for a weapon with `ScatterRadius` or infantry inaccuracy are missing. `golden_wp55_fire` replaces the C++ function the same way, so no vector covers it.
- `player_relationship` models player-to-player relationships only. C++ `Team::getRelationship` and `Player::getRelationship` first look up per-team and per-player overrides (`m_teamRelations`, `m_playerRelations`); (The port's implicit self-alliance matches the usual setup: `PlayerList::newGame` sets each player as its own ally.)
- `FiringTracker` is attached but nothing ported reports a shot to it (`Object::fireCurrentWeapon` is reached from the unported AI), so it only sleeps. Before it is wired, its sim host needs `reload_all_ammo` to use `load_ammo_now`/`reload_ammo` as `Object::reloadAllAmmo` does (it now only fills the clip), and its `xfer`/`load_post_process` need the live sleepy schedule. `golden_wp3_3b_combat_leaves` covers the tracker against a mock host only.
- `set_weapon_set_flag` does not rebuild the weapon set, and spawn picks the set with empty flags. C++ `updateWeaponSet` uses the object's flags and runs again on every change.
- A weapon that sits in a weapon set has to be fired on a copy and written back. No production code does this yet.
- Weapon firing leaves out `DAMAGE_DEPLOY`'s assault order, `processRequestAssistance` and the victim effects of `DAMAGE_DISARM`.
- **`PKT-216 FireWeaponPower` is not bit-exact**, although `PORT_MAP.md` counts it. It fires at once, where C++ reloads all ammo and orders the unported AI to attack.
- `Weapon::transfer_next_shot_stats_from` copies the stored status; C++ copies `getStatus()`, which refreshes it first. It has no callers.
- `set_geometry_info` stores the geometry and re-registers with the partition grid, but does not tell the drawable as C++ `Object::setGeometryInfo` does.
- `ProjectileStreamUpdate::add_projectile` has no caller until weapon projectiles are ported.
- `RadiusDecalUpdate::create_radius_decal` has no caller, and takes a template name because decal templates are not ported.

- `TunnelTracker` loading (player or cave): C++ reads the passenger ids aside and `loadPostProcess` re-adds each one (recounting heroes, leaving the group, partition and pathfind map). Rust reads them straight into the list, so the hero count stays 0. No vector covers a tracker, `CaveSystem` or `CaveContain` load.
- `TunnelContain` leaves out `Object::setSafeOcclusionFrame` and `AcademyStats::recordUnitEnteredTunnelNetwork` (a saved player counter); the sim holds neither.
- Passenger orders: `order_all_passengers_to_exit` ignores `instantly` (`aiExitInstantly` leaves at once), `order_all_passengers_to_idle` takes no command source and sends `CMD_FROM_AI`, and the AI's own effects of an exit order (the rider registering `WANTS_TO_EXIT`, ignoring the order when subdued) are missing. `gen_pkt300_tunnel.cpp` excludes the instant form and withdraws the registration.
- While a tunnel's or cave's own module executes, `SimView::contain_count`, `contain_max` and `contain_items` of that object answer from its empty `OpenContain` state, not the shared tracker.
- `OpenContain::addToContain` leaves out `checkAndDetonateBoobyTrap`.
- Neither `golden_pkt300_tunnel` nor `golden_pkt264_cave` covers `onCollide`, door exits, tracker loading, a tunnel as a passenger or scheduler-driven updates.

- A null `Team*` is `TeamId::INVALID`, which only a cave defecting to no team produces. `capture_object` and `defect_object` handle it, but `player_index(TeamId::INVALID)` answers 0, the neutral player, where C++ has no controlling player. Code that reads a teamless object's player has not been checked.
- `defect_object` leaves out the end of `Object::defect` that moves the object's mines to the new team.
- `CaveContain` does nothing where the reference dereferences a null tracker, and `CaveSystem` ignores a negative index, where the reference runs out of memory. A map or script with such a cave would crash the original.
- `Player` calls `recalcApparentControllingPlayer` on containers; only the `StealthUpdate` half is wired (garrisons).
- `FireSpreadUpdate`: `OCLEmbers` goes through `spawn_ocl`, which only records the call, so the objects an embers list creates and their PRNG draws are missing.
- `FlammableUpdate` plays no burning sound (client audio).
- `FlammableUpdate` takes its own aflame damage while executing. `attempt_damage_watching` replays that one `onDamage`; further damage to the same object from inside that call chain would not reach the module.
- `set_wake_frame` saturates where C++ wraps, and the scheduler does not read a sleep above `0x7fffffff` as negative, as the signed `UpdateSleepTime` does. No fire-module INI duration reaches either.
- Docks: no models are loaded, so every dock behaves as boneless. Enter, dock, exit and waiting positions differ from retail, and they are saved. Loading a retail save re-zeroes the fixed waiting positions.
- `RailedTransportDockUpdate` and `PrisonDockUpdate` are unported: `set_dock_open` / `set_dock_crippled` do nothing on them and they read as open.
- No supply truck AI is ported, so nothing drives a dock. An AI port must implement `supply_truck()`. The warehouse's `getBoxesStored` / `setCashValue` have no `SimApi` route yet. A dock whose module is executing is not found by `dock_slot`.
- `find_position_around` lacks the cliff-cell and path-exists checks.
- `PhysicsBehavior`: `processCollision` always answers FALSE and the ignored obstacle defaults to invalid (no AI); `carrier_deck_height` is always 0; a contain module's own mass omits its passengers while it executes; `MinFallHeightForDamage` is converted with the gravity at object construction, not at INI parse; no bounce sound or `transferObjectName`. Not covered by vectors: a real AI or projectile update, non-ground layer heights, crash-weapon effects, frames above 2^24, ordering between modules.
- `fire_weapon_template` records a shot even when the C++ temporary weapon would refuse (frames above 2^24).
- Stealth: `ObjectRecord::script_status` and `ai_last_command_source` have nothing that sets them; radar object list and radar events (saved by the original) are not modelled; the client PRNG draw for the pulse phase matches only when the stream is reseeded. Mark, grant and disguise calls are skipped when the target module is executing. Not wired from unported callers: `SpecialAbilityUpdate`, `BattlePlanUpdate`, `SlavedUpdate`, `OverlordContain`, `RiderChangeContain`, `SpawnBehavior`, and the disguised-player lookups in `Player`, the partition and weapon sets.
- `Object::setStatus(UNDER_CONSTRUCTION)` does not detonate mines.
- Production exits: `pathfinder_adjust_destination` tries only the goal cell (no spiral search, footprints, reservations, zones or logical extent), and cell clamping assumes the pathfind extent starts at 0. `aiFollowExitProductionPath` is only recorded (`exit_path_orders`), so an AI port must dispatch it, with its refusals. Spawn points come from `SimWorld::pristine_bones`, which nothing fills: `SpawnPointProductionExitUpdate` refuses every reservation until models are loaded. `isDoingGroundMovement` uses the first locomotor of the set. No `SimApi` method reserves or unreserves a door. Not covered by vectors: a failing goal adjustment, real bridges, water-only locomotors, loading a C++ save.
- Money and upgrades are keyed by team, not player: a player's second team has its own purse and upgrades.
- `StructureToppleUpdate` feeds the client random stream into logic, and the port does not model client-side draws by effects and particles, so burst timing can differ from the original. This is also a likely desync hazard in the original.
- Toppling: `BoneFXUpdate` is unported (call only recorded); scripted topple directions are keyed by object id (no object names, no script action sets them); nothing sets construction percent yet; only collision calls `topple_object`; an unknown `StumpName` makes no stump where C++ throws. Not covered by vectors: pathfind removal on sideways toppling, deselect, contained or observer visibility, loading a save.
- `selectObject` is only recorded (`world.selected_objects`). Weapon firing's assistance request is unported (entry point `request_assist_from`). `SpectreGunshipUpdate` is unported: the gunship's power order reaches the recorded stand-in. `HordeUpdate::joinOrLeaveHorde` has no caller and is not ported. There is no `onDrawableBoundToObject` hook. An AI port must take over `evaluate_morale_bonus` and implement the healing, attack and slot-enabled orders. Not verified: `isAbleToAttack` through spawn slaves or a subdued slaver, loading a save, horde update rate 0.
- Minefields: `fire_weapon_template` and `spawn_ocl` only record, so ported mines hurt nobody yet. Nothing calls `disarm`, `set_minefield_target` or scoot parameters from a creation list. A module can now lend itself back to the arena (`lend_self`) so its own callbacks run in C++ order; only a plain `ActiveBody` does so for land mines. `ai_is_clearing_mines` answers FALSE while that AI module executes. `ai_goal_object` holds an arena slot where C++ holds an ID, so a stale goal could resolve to a newer object. Standard minefield distance and density are read at use, not at INI parse. No map loader fills `CliffMap`. Not verified: detonation weapon effects, wrapper bodies on a mine, tilted objects, damaged bridges.
- Special abilities: `ActionManager` is unported (answers come from `world.action_permissions`); there is no `CommandButton` / `CommandSet` INI parser (`rules.command_store` is filled by code); `attack_priority_distance_modifier` is not read from AIData. `StickyBombUpdate` is unported, so charges are created but never stick or detonate. Line of sight is always clear. Skill points and building captures are only totalled. `doCommandButtonAtObject` covers only the special power and enter commands a hunt gives. An AI port must implement the new orders and set `ai_last_command_source`.
- Spawning and slaves: `setDisabledUntil(UNMANNED)` on a non-drone is unported, as are its rider propagation and audio; defecting still lacks production cancel, parked-unit defection and mine re-teaming. Weapon attack questions are answered from `SimWorld::attack_abilities` when it has an entry. `scoreTheKill` is only recorded and `onUnitCreated` assumes scoring is enabled. An AI port must supply the idle state, path destination and new orders; `ai_go_prone` already forwards to `ProneUpdate`. Unported callers: creation-list `onEnslave`, `AIGroup`, `ActionManager`, `Weapon`, `MobMemberSlavedUpdate`. `health_box_offset` is not in any object save.
- Projectiles launch from the launcher's transform (no launch bones or turret offsets). Detonation runs the weapon state machine, but `fireWeaponTemplate` is unported and only recorded in `projectile_detonations`, so no damage is dealt. The collide filter lacks `JetAIUpdate` sneaky-target immunity. Wall footprints only record membership. Terrain heights along a line are computed on demand, not cached at load. `team_colors` / `team_sides` are filled by nothing.
- Production: money, upgrades and energy are keyed by team, not player (score and academy records are by player) (`grant_player_upgrade` refreshes only one team's objects). `spawn_object` neither draws `BuildVariations` nor runs upgrade modules; only `factory_new_object` does. `CommandSet` / `CommandButton` INI is not parsed. Nothing fills handicaps, cost or time changes, build bans or buildable overrides. `completed_upgrades`, `units_produced` and `object_count_changed_frame` are stand-ins. No command, AI or script queues anything yet; selling must call `cancel_and_refund`; the destructor's door unreserve does not run. Parking and create modules are still scripted in its vectors; the three exits are now checked together with it.
- `PORT_MAP.md` counts packets by file, not completeness. `PKT-143 Locomotor` has no movement code (the C++ has 15 movement functions), `PKT-399 Weapon` lacks `fireWeaponTemplate`, `TurretAI` is not connected to the simulation, and the real ground-height code lives in `GameEngineDevice`, outside the manifest.
- AI slice S0: nothing outside its test calls `run_frame`; the path queue is a recorded tape until slice S5; `PathUnitQueries` and `MapTerrain` are signatures only. Orders still arrive through facet methods, so a call back during an order is skipped (S8). `ai_construct` does not ask for the next frame as the constructor does. `Player::onPowerBrownOutChange` and the rest of `Player::update` are seams. The AI's own save bytes and a game-wide CRC are not compared.
- Parking, silo, laser and battle plan: `JetAIUpdate` and the AI turret are test stand-ins (an aircraft AI port must provide `jet_ai`); `set_weapon_set_flag` builds only the first weapon set; projectiles get no battle plan bonus at launch; player battle plan state must join `Player` save and CRC when `Player` is ported; no battle plan or silo sounds, messages or radar events; spaces beyond four doors report no door; loading a save does not re-hold production doors.
- Found by running ported modules together: `Player::onPowerBrownOutChange` is unported (radar off, powered objects disabled), which matters now that spawning counts base energy; nothing adds power when construction completes; `spawn_object` callers still skip build variations and upgrade modules; player upgrade granting exists twice and walks world order where the original walks team member lists; `player_captured_objects` sits beside the score keeper. Not covered by any vector: unsellable clearing on capture, the granted-upgrade academy record, money earned from crates, sabotage and the cash hack.
- `setDisabledUntil` / `clearDisabled` do not propagate to a contain module's rider; the veterancy weapon bonus conditions are never set; weapon firing must not write a stale weapon copy back over a retime caused by the firing tracker (the tracker's host change has no test). `HistoricBonusTime` and `FireSoundLoopTime` are not parsed.
- Second joined check: `friend_bindToDrawable` also sets night and snow model conditions (not ported). The cash hack's floating text is a client event in Rust and its position and amount are not compared. The load-time rebuild of the sleepy update heap is unverified, as are whole-object and whole-world loads, helper module loads, weapon damage from mines, and die modules other than `DestroyDie` and the helicopter slow death.
