# Open Decisions and Known Port Gaps

Found while porting modules mechanically. Each needs an owner decision or a later spine change. Delete an entry once it is resolved.

## Decisions

1. **Where dock state lives. Settled 2026-11-27 (follow the C++):** in the dock module, reached through `DockFacet`. The `dock_closed` / `dock_crippled` stand-ins are gone.
2. **Default `XferSave` version.** The reference library is built with `RETAIL_COMPATIBLE_XFER_SAVE=1`, so `PoisonedBehavior` saves version 2. With `retail-xfer-save` off, the crate writes version 3. `golden_wp53_c1` strips the appended source id and compares it separately; `FlammableUpdate` (version 1 against 2) is handled the same way in `golden_pkt330_327_fire`. Should default features match 0 or 1?
3. **AI random-number draws.** `AIUpdateInterface` is unported. Its draws are imitated in `sim/mod.rs` (`ai_construct`, `ai_init_state_machine`, `ai_idle`). The real port must take them over.
4. **Shared and redirected passenger lists. Decided 2026-11-26 (owner: do what a faithful port does).** The contain getters now take `(sim, ctx)`, as the C++ virtuals reach the tunnel tracker and the rider's contain module. `PKT-300` and `PKT-264` are ported; `PKT-284` is unblocked.
5. **Containment override hooks. Decided 2026-11-26: yes, follow the C++ virtual calls.** `ContainBehavior` has hooks for `addToContainList`, `removeFromContain` and the list getters, but not yet for `addToContain`, `isEnclosingContainerFor` or `isSpecialOverlordStyleContainer`. Add those with the `OverlordContain` port. `HelixContain` (`PKT-275`) implements the facets itself.
6. **Settled 2026-11-27 (follow the C++):** `LandMineFacet::set_scoot_parms` takes the sim and context.
7. **Settled 2026-11-27 (follow the C++):** the overlap query, footprint operations and cliff cells that minefield placement needs are ported.
8. **Where a bridge's tower table lives. Settled 2026-11-27 (follow the C++):** in the `BridgeBehavior` module, reached through `BridgeFacet`. `link_bridge_tower` and `SimWorld::bridge_links` are removed.
9. **Where barrel counts come from.** `Weapon::privateFireWeapon` reads `Drawable::getBarrelCount`, which comes from the model's bones, and the result is saved with the weapon. The port loads no models, so `ObjectRecord::weapon_barrel_count` stays 0 outside tests. Replay parity needs the counts from somewhere.
10. **How ported Rust reaches the playable game. Decided by the owner, 2026-11-27: the whole game is to be Rust, with no C++.** So the port aims past the headless simulator at its own client, the unit AI is in scope (item 11), and swapping modules into the C++ engine is a testing tool, not the route. Working assumption until the owner says otherwise: the C++ build stays as the reference that Rust output is compared with, and ships in nothing.
    - **Size, rough upper bound** (lines of C++ in `Core` and `GeneralsMD/Code`, headers included): in the port plan, 138k in packets marked implemented (some partial) and 191k unported; outside the plan, 218k 3D engine libraries, 144k game client, 109k device layer, 50k network, 28k other. Editors and tools (289k) are not needed to play. Third-party C/C++ under the game (graphics translation, windowing, audio, video) is not counted.
    - **Still open:** item 12.
    A trial of (b) with one module was done on 2026-11-27:
    - **It works.** The unmodified Rust `LifetimeUpdate` (`PKT-339`) runs in the engine and all 996 checkpoints match.
    - **One-off cost, now paid:** `scripts/gen_engine_sim.py` writes the `SimView`/`SimApi` impl (293 methods; unconnected ones abort with their name), plus about 100 hand-written lines in `engine_sim.rs`.
    - **Per-module cost in that trial:** about 60 lines of Rust entry points and 120 lines of C++ for 7 connected methods (the shared bridge below has since taken most of the C++). The C++ module still owns the state, `crc` and `xfer`, so each further field has to be passed both ways.
    - **The limit:** methods that return references into Rust-owned data cannot be answered by a callback (the value-accessor trial below is a way round it for `object`; the numbers here predate it). Counted over the classes the replays create (`SWAP_CANDIDATES.md`, `scripts/swap_candidates.py`): only 15 of 97 ported classes (837 of 14,039 instances) reach none. `object` is reached by 80 and is the only blocker for 24; `rules` by 56. Outside `sim/mod.rs` there are 434 `object`, 23 `object_mut` and 140 `rules` call sites.
    - **Five more were run the same day** (`SupplyWarehouseCreate`, `ArmorUpgrade`, `ModelConditionUpgrade`, `RadarUpdate`, `PowerPlantUpdate`). All 996 checkpoints match with all six modules in, and the Rust modules are unmodified. Call counts and faults are in `BASELINE.md`.
    - **What the replays proved:** only `SupplyWarehouseCreate` has its effect checked (its fault fails all six). `ArmorUpgrade` and `ModelConditionUpgrade` are never called, so their run proves nothing. For `RadarUpdate` and `PowerPlantUpdate` only the wake and sleep values are checked, apparently through update order; their members and model conditions can be wrong and the check still passes, and `PowerPlantUpdate`'s `extendRods` and `update` never run.
    - **Cost per module** (lines of Rust entry points + their tests + C++): warehouse 27 + 14 + 15; armor 26 + 19 + 26; model condition 32 + 16 + 17; radar 69 + 59 + 38; power plant 60 + 65 + 46. Each also needs about 12 lines in `build_rust_engine.py` and a few in `zh_ffi.h`.
    - **Adapter growth, once:** five more connected methods (45 lines in `engine_sim.rs`), a shared C++ bridge (138 lines, `zh_ffi_engine_sim.inc`; `LifetimeUpdate`'s own C++ fell from 116 lines to 62) and a shared test engine (89 lines).
    - **Left in C++:** the upgrade mux (conditions, FX, removals, executed flag), the `CreateModule` base, the walk over players' supply managers, and every `crc` and `xfer`. The ported `ArmorUpgrade` omits the chemical-suit terrain decal, a client-only call that `ClientSink::on_terrain_decal` could carry; C++ still makes it.
    - **Upgrade modules are mostly unverifiable with these replays:** `upgradeImplementation` is never called for seven other upgrade classes in the candidate table either. Instance counts say how many objects carry a module, not how often it runs.
    - **Value accessors, trial of 2026-11-27:** `object()` field reads can become named `SimView` methods returning values; the adapter wires those it connects and the rest abort by name. Do not mirror `ObjectRecord` in the adapter (unfilled fields would be silently wrong). `DefaultProductionExitUpdate` (`PKT-315`) now runs in the engine this way, 996 checkpoints matching; calls and faults are in `BASELINE.md`.
        - **Cost:** 3 accessors (`object_transform`, `object_orientation`, `object_layer`); 1 call site (a shared helper), 4 lines changed; 29 lines added to `sim/mod.rs`; about 25 Rust and 20 C++ adapter lines for the three. The module's other 9 methods and its second object cost far more: in all, 114 lines in `engine_sim.rs`, 96 entry + 71 test lines, 60 in the test engine, 27 in `zh_ffi.h`, 185 of C++.
        - **Unblocked:** this class only (15 to 16 classes with no data method, 837 to 975 instances). The queue, supply-center and spawn-point exits share the helper but have 1 or 2 reads of their own.
    - **Converting the rest** (scripted from source text, outside `sim/mod.rs` and tests): 544 `object` sites in 123 files (433 if only one-line `sim.object(` is counted) read 54 distinct member paths over 42 first members; the top 10 cover 575 of 761 reads. 24 `object_mut` sites need about 13 setters.
        - **Mechanical:** 411 sites read one path and 6 only test existence. 123 read two to five paths. No function outside `sim/mod.rs` takes or returns an `ObjectRecord`. 39 bindings stay live across other sim calls, which is harmless: the borrow allows only `&self` calls in between, so reading later returns the same value.
        - **Not mechanical:** 83 sites read arena slots or `behaviors` (39; an engine has no slot to give, so each needs a question such as `object_has_ai`) or aggregates such as `geometry` (48 reads) and `weapon_set` (the adapter would have to rebuild the struct). 5 sites hold or hand on the record in ways the script does not follow.
        - **Estimate, not measured:** about 50 accessors, some already existing under other names, at about 9 lines each in `sim/mod.rs`, plus 568 edited sites. Adapter and C++ lines are paid only for accessors a swapped module needs.
    - **`rules()`, count only:** 163 sites in 58 files reach 12 registry members: `thing_factory` 51, `global_data` 24, `weapon_store` 12, `special_power_store` 8, `upgrade_center` 7, `name_keys` 6, `command_store` 5, 4 others once each; 46 hand the whole registry on (mostly to the upgrade mux). 55 bind the result to a name. Rules are immutable parsed data, so filling a Rust registry in the engine is a possible route that does not exist for objects; it is untried.
    - **Recommendation:** use the accessor pattern, converting only what the next swapped module needs; no bulk pass. `object` is not the redesign it looked like. `rules` (56 classes) is now the larger blocker, and C++ still owns members, `crc` and `xfer` of every swapped module. Use the adapter for leaf modules where running in the real engine is worth it as a check on the port; do not yet plan on it to move the simulation into the game. Playing the game does not depend on either, and a swap changes nothing the player sees.
11. **Porting the unit AI. In scope since item 10 was decided (2026-11-27)**; it follows weapons and movement. `AI_PORT_PLAN.md` splits it into slices of about 40 workers (12 to 20 million tokens before rework, an estimate); the first moving unit is about 15. It serves a headless simulator, not the playable game (item 10). Working assumptions until the owner says otherwise: reproduce the retail pathfinding and AI-group quirks the reference runs; leave computer opponents and real map loading for later; keep item 2 as it is. Only slice S0 is being started.
12. **External crates for the client.** The workspace has none, and that suits the simulation. A window, graphics, audio and video in Rust either need crates (which wrap the operating system's libraries) or hand-written bindings to those libraries. **Owner (2026-11-27): ask when it is needed.** Not decided yet: before the first external crate is added, ask, naming the crates and what they are for. Client work that needs no crate, and simulation work, do not wait for it.

## Known gaps

- A module cannot be re-entered while it executes. `SupplyWarehouseCripplingBehavior` and `TechBuildingBehavior` apply their own self-callbacks inline instead.
- `BridgeScaffoldBehavior`: zero speed on a zero-length leg gives NaN positions. The reference then destroys the object from outside the module; Rust does not. `gen_wp53_c1.cpp` excludes those inputs, so no vector covers this.
- An unknown `PulseFX` name stays set in Rust but becomes null in C++.
- `capture_object` / `set_object_team` leave out the rest of `Object::onCapture`: `cancelAllTasks` on a dozer, clearing the `SCRIPT_UNSELLABLE` status and a skirmish AI selling a captured faction building.
- With `retail-crc`, `WeaponTemplate::get_delay_between_shots` returns the maximum when the minimum exceeds it; the retail PRNG helper draws a value there. The default build matches.
- `FloatUpdate` over dry ground: C++ writes an uninitialised `waterZ` to the object, so there is no value to match. The port writes 0.
- `ProneUpdate` skips the model condition for an object without a drawable, where C++ would crash.
- `PKT-307`, `PKT-343` and `PKT-364` are header-only manifest entries for modules ported under another packet (`PKT-308`, `PKT-281`, `PKT-233`). `PORT_MAP.md` still lists them as unported.
- Weapons deal damage (`object/weapon_effects.rs`, `golden_pkt399_weapon_effects`: range checks, scatter, radius damage and its filters, shock wave, delayed damage, historic bonus, projectile launch and detonation, streams, lasers). Still missing: a projectile with no `ProjectileUpdateInterface` is placed at its destination, which includes every `MissileAIUpdate` projectile, so missiles never detonate; `FireOCL` and `ProjectileDetonationOCL` only record through `spawn_ocl`; fire FX, recoil and sounds are one `ClientSink::on_weapon_fire` call. Where C++ dereferences a destroyed source (historic bonus, radius-less `SUICIDE`), the port does nothing. The countermeasures report and the battle plan bonus at launch have no reference vector (the latter has a Rust test). `Object::initObject` also gives every new object its player's active battle plan bonuses; the port's spawn does not. The shock wave is ported, the radar under-attack event after it is not.
- `world.weapon_fires` and `world.projectile_detonations` are test logs that nothing empties. `world.weapon_templates_stubbed` lets `golden_wp55_fire` and `golden_pkt341_350_309_support`, whose oracles replace `fireWeaponTemplate`, skip it. In `zh_ffi` the new weapon methods are not wired.
- `player_relationship` models player-to-player relationships only. C++ `Team::getRelationship` and `Player::getRelationship` first look up per-team and per-player overrides (`m_teamRelations`, `m_playerRelations`); (The port's implicit self-alliance matches the usual setup: `PlayerList::newGame` sets each player as its own ally.)
- Weapon firing (S13, `golden_s13_weapon_firing`): `Object::fireCurrentWeapon`, `preFireCurrentWeapon` (`object/weapon_actions.rs`) and the range, line of sight, pitch and damage estimate questions (`object/weapon_queries.rs`) are called by the attack states (S14); the approach target still has no caller. A shot works on a copy of the stored weapon that is written back before the firing tracker is told, so callbacks during the shot see the weapon as it was. Asked through `AiSeams` and answered with nothing by default: the sneaky targeting offset, bridge attack points (the default is what the reference does without a bridge record), aircraft destination adjustment and the assault order. Not covered by vectors: bridge records, an aircraft that adjusts, spawn slaves in the damage estimate, the supersonic test before countermeasures, the firing tracker's own update, loading a save. The reference saves version 1 of the tracker and the default build version 2 (item 2); its load does not restore the live schedule. The looping fire sound's key is not passed to the tracker.
- `set_weapon_set_flag` does not rebuild the weapon set, and spawn picks the set with empty flags. C++ `updateWeaponSet` uses the object's flags and runs again on every change.
- `Weapon::transfer_next_shot_stats_from` copies the stored status; C++ copies `getStatus()`, which refreshes it first. It has no callers.
- `set_geometry_info` stores the geometry and re-registers with the partition grid, but does not tell the drawable as C++ `Object::setGeometryInfo` does.
- `RadiusDecalUpdate::create_radius_decal` has no caller, and takes a template name because decal templates are not ported.

- `TunnelTracker` loading (player or cave): C++ reads the passenger ids aside and `loadPostProcess` re-adds each one (recounting heroes, leaving the group, partition and pathfind map). Rust reads them straight into the list, so the hero count stays 0. No vector covers a tracker, `CaveSystem` or `CaveContain` load.
- `TunnelContain` leaves out `Object::setSafeOcclusionFrame` and `AcademyStats::recordUnitEnteredTunnelNetwork` (a saved player counter); the sim holds neither.
- Passenger orders: `order_all_passengers_to_exit` ignores `instantly` (`aiExitInstantly` leaves at once), `order_all_passengers_to_idle` takes no command source and sends `CMD_FROM_AI`, and the AI's own effects of an exit order (the rider registering `WANTS_TO_EXIT`, ignoring the order when subdued) are missing. `gen_pkt300_tunnel.cpp` excludes the instant form and withdraws the registration.
- While a tunnel's or cave's own module executes, `SimView::contain_count`, `contain_max` and `contain_items` of that object answer from its empty `OpenContain` state, not the shared tracker.
- `OpenContain::addToContain` leaves out `checkAndDetonateBoobyTrap`.
- Neither `golden_pkt300_tunnel` nor `golden_pkt264_cave` covers `onCollide`, door exits, tracker loading, a tunnel as a passenger or scheduler-driven updates.

- A null `Team*` is `TeamId::INVALID`, which only a cave defecting to no team produces. `capture_object` and `defect_object` handle it, but `player_index(TeamId::INVALID)` answers 0, the neutral player, where C++ has no controlling player. Code that reads a teamless object's player has not been checked.
- `defect_object` leaves out the end of `Object::defect` that moves the object's mines to the new team.
- `CaveContain` does nothing where the reference dereferences a null tracker, and `CaveSystem` ignores a negative index, where the reference runs out of memory. A map or script with such a cave would crash the original.
- `Player` calls `recalcApparentControllingPlayer` on containers; only the `StealthUpdate` half is wired (garrisons).
- `FireSpreadUpdate`: `OCLEmbers` goes through `spawn_ocl`, which only records the call, so the objects an embers list creates and their PRNG draws are missing.
- `FlammableUpdate` plays no burning sound (client audio).
- `FlammableUpdate` takes its own aflame damage while executing. `attempt_damage_watching` replays that one `onDamage`; further damage to the same object from inside that call chain would not reach the module.
- `set_wake_frame` saturates where C++ wraps, and the scheduler does not read a sleep above `0x7fffffff` as negative, as the signed `UpdateSleepTime` does. No fire-module INI duration reaches either.
- Docks: no models are loaded, so every dock behaves as boneless. Enter, dock, exit and waiting positions differ from retail, and they are saved. Loading a retail save re-zeroes the fixed waiting positions.
- `RailedTransportDockUpdate` and `PrisonDockUpdate` are unported: `set_dock_open` / `set_dock_crippled` do nothing on them and they read as open.
- No supply truck AI is ported, so nothing drives a dock. An AI port must implement `supply_truck()`. The warehouse's `getBoxesStored` / `setCashValue` have no `SimApi` route yet. A dock whose module is executing is not found by `dock_slot`.
- `find_position_around` lacks the cliff-cell and path-exists checks.
- `PhysicsBehavior`: `processCollision` always answers FALSE and the ignored obstacle defaults to invalid (no AI); `carrier_deck_height` is always 0; a contain module's own mass omits its passengers while it executes; `MinFallHeightForDamage` is converted with the gravity at object construction, not at INI parse; no bounce sound or `transferObjectName`. Not covered by vectors: a real AI or projectile update, non-ground layer heights (`golden_s7_locomotor_movement` runs a raised layer over synthetic terrain), crash-weapon effects, frames above 2^24, ordering between modules.
- Stealth: `ObjectRecord::script_status` and `ai_last_command_source` have nothing that sets them; radar object list and radar events (saved by the original) are not modelled; the client PRNG draw for the pulse phase matches only when the stream is reseeded. Mark, grant and disguise calls are skipped when the target module is executing. Not wired from unported callers: `SpecialAbilityUpdate`, `BattlePlanUpdate`, `SlavedUpdate`, `OverlordContain`, `RiderChangeContain`, `SpawnBehavior`, and the disguised-player lookups in `Player`, the partition and weapon sets.
- `Object::setStatus(UNDER_CONSTRUCTION)` does not detonate mines.
- Production exits: without a pathfind map, `pathfinder_adjust_destination` tries only the goal cell (no spiral search, footprints, reservations, zones or logical extent), and cell clamping assumes the pathfind extent starts at 0; with a map the S4 search runs. `aiFollowExitProductionPath` is only recorded (`exit_path_orders`), so an AI port must dispatch it, with its refusals. Spawn points come from `SimWorld::pristine_bones`, which nothing fills: `SpawnPointProductionExitUpdate` refuses every reservation until models are loaded. `isDoingGroundMovement` uses the first locomotor of the set. No `SimApi` method reserves or unreserves a door. Not covered by vectors: a failing goal adjustment, real bridges, water-only locomotors, loading a C++ save.
- Money, upgrades and energy belong to the player (`golden_player_state`), but other `Player` members are still keyed by team, so a player's second team has its own: sciences, radar counts and disabling, cost modifiers, handicaps, production cost and time changes, build bans, bounty percent, captured-object count, shared special power timers, attacked-by, preorder, human and skirmish-AI flags. `Player::xfer` is unported, so the order of its upgrade list and `Money`'s income buckets are not kept. Nothing ports `TeamFactory`: team prototypes exist only through `add_player_team` / `add_team_instance`, and a team in no list walks as its own prototype (default team first, then by id).
- `StructureToppleUpdate` feeds the client random stream into logic, and the port does not model client-side draws by effects and particles, so burst timing can differ from the original. This is also a likely desync hazard in the original.
- Toppling: `BoneFXUpdate` is unported (call only recorded); scripted topple directions are keyed by object id (no object names, no script action sets them); nothing sets construction percent yet; only collision calls `topple_object`; an unknown `StumpName` makes no stump where C++ throws. Not covered by vectors: pathfind removal on sideways toppling, deselect, contained or observer visibility, loading a save.
- `selectObject` is only recorded (`world.selected_objects`). `SpectreGunshipUpdate` is unported: the gunship's power order reaches the recorded stand-in. `HordeUpdate::joinOrLeaveHorde` has no caller and is not ported. There is no `onDrawableBoundToObject` hook. An AI port must take over `evaluate_morale_bonus` and implement the healing, attack and slot-enabled orders. Not verified: `isAbleToAttack` through spawn slaves or a subdued slaver, loading a save, horde update rate 0.

Nothing calls `disarm`, `set_minefield_target` or scoot parameters from a creation list. A module can now lend itself back to the arena (`lend_self`) so its own callbacks run in C++ order; only a plain `ActiveBody` does so for land mines. `ai_is_clearing_mines` answers FALSE while that AI module executes. `ai_goal_object` holds an arena slot where C++ holds an ID, so a stale goal could resolve to a newer object.
